Bean的生命周期

  1. 实例化 Bean：Bean 容器根据配置文件中的 Bean 定义，通过反射机制创建 Bean 的实例。

  2. 设置属性和依赖：为 Bean 设置相关的属性和依赖项。

  3. 初始化 Bean：

    • 检查是否实现了相关的 Aware 接口，并设置相应的依赖。
    • 检查bean是否实现了 BeanPostProcessor 接口进行前置处理。
    • 如果 Bean 实现了 InitializingBean 接口，调用其 afterPropertiesSet() 方法。
    • 如果在配置文件中定义了 init-method，则执行相应的方法。
    • 如果需要在初始化后执行操作，可以实现 BeanPostProcessor 接口进行后置处理。

    Bean 被容器管理并在程序中使用。

    销毁 Bean：

    • 如果 Bean 实现了 DisposableBean 接口，则调用 destroy() 方法销毁bean，没有实现接口就检查配置文件是否指定destroy-method 指定就调用对应的销毁方法销毁bean

    如果两个都没实现，Spring将不会执行任何销毁操作，导致bean的资源不会被自动释放，会出现oom或资源占用的问题

SpringBoot的启动流程

  1. 555启动main方法 从main方法启动，并通过SpringBootApplication.run()会初始化一个SpringApplication对象.
  2. 运行SpringApplication的过程中Spring Boot 会创建应用的监听器并开始监听启动过程中发生的事件，SpringBoot会创建和配置一个 Environment，用来加载系统变量、环境变量、配置文件等，确定应用环境，然后根据应用类型选择合适的 ApplicationContext，并将环境变量、监听器与应用上下文关联起来。
  3. Spring Boot 会扫描项目中定义的所有 Bean，并将它们注册到 Spring 容器中。自动配置和手动配置的 Bean 也会在此时加载。
  4. 如果是 Web 应用，Spring Boot 会启动嵌入式服务器（如 Tomcat 或 Jetty），并初始化相关 Web 组件。
  5. 所有初始化和配置完成后，Spring Boot 会显示启动成功的日志，整个应用正式进入运行状态。

什么是SpringBoot

SpringBoot是简化spring应用程序开发的框架，它的主要目标是减少Spring应用程序的配置和开发复杂性，使我们快速构建、测试和部署Spring应用

Spring Boot 的核心特性可以概括为以下几点

  1. 自动配置（Auto-Configuration）：Spring Boot 会根据项目中添加的依赖自动配置 Spring 应用的常用组件，避免了手动配置，简化了开发流程。
  2. Starter 依赖（Starter Dependencies）：Spring Boot 提供了一组“Starter”依赖，开发者只需引入这些依赖，就能快速集成相关功能，无需繁琐的依赖管理。
  3. 内嵌服务器（Embedded Server）：Spring Boot 支持内嵌的 Web 服务器（如 Tomcat、Jetty、Undertow），可以直接将应用打包成一个可执行的 JAR 文件，启动时无需外部应用服务器。
  4. 无 XML 配置：Spring Boot 倾向于使用 Java 注解和 Java 配置类进行配置，减少了传统 Spring 中复杂的 XML 配置文件。
  5. 简化的开发和部署：Spring Boot 应用可以通过单个命令（如 java -jar app.jar）运行，简化了应用的开发和部署过程，适合快速迭代。

Spring Boot 支持多种内嵌服务器

  1. Apache Tomcat：默认的内嵌服务器，适合大多数 Web 应用开发，支持 Servlet 和 JSP。
  2. Jetty：一个轻量级的服务器，适合需要高性能和可嵌入性应用的场景，特别是微服务架构中。
  3. Undertow：一个灵活的、轻量级的 Web 服务器，支持异步处理，适用于高性能应用和微服务。
  4. Netty：一个非阻塞的异步事件驱动网络应用框架，通常用于高性能的网络应用开发。

Spring Boot 中 application.properties 和 application.yml 的区别是什么？

对于配置而言效果是一样的，区别就是书写格式

application.properties 使用键值对配置，键和值之间用等号或冒号分隔

application.yml 使用YAMl格式，具有层次结构，使用缩进表示嵌套关系，适合复杂配置，阅读性更好

Spring Boot 配置文件的加载顺序

优先级最高的是命令行参数通过 java -jar 启动时传入的命令行参数>JAR 包外的application-{profile}-properties>JAR包内的application-{profile}-properties>jar包外的application-properties >JAR包内的application-properties

注意如果application.properties、application.yml两个文件同时存在，properties优先级会高一些，相同名称的配置，会将yml内的配置覆盖掉。当我们使用Bootstrap.yml连接配置中心的配置信息，因为bootstrap.yml是在spring应用上下文刷新之前就会被加载。所以Bootstrap.yml 的优先级要高于application.yml,后加载的application.yml不会覆盖相同的配置信息

Spring Boot 打成的 jar和普通的 jar 有什么区别

  1. Spring Boot 项目最终打包成的 jar包含了内嵌的服务器和 Main-Class 指定的启动类 这种 jar 可以直接通过 java -jar 命令来运行
  2. 目录结构不同，无法作为依赖使用：Spring Boot 使用 Spring Boot Maven/Gradle 插件进行打包，生成的 JAR 结构与普通 JAR 不同，应用代码位于 BOOT-INF/classes，依赖库位于 BOOT-INF/lib 中。而普通 JAR 文件通常将所有类和资源文件直接放在 JAR 根目录下。因此，Spring Boot 的 JAR 包含的依赖管理和目录结构使它无法被其他项目直接依赖使用。

如何理解Spring Boot中的starter

在SpringBoot中，starter是一组有用的依赖集合，用于简化构建配置。SpringBoot通过Starter Pom提供了各种常用功能模块的集成，我们只需引入一个Starter依赖，便可以获得该模块的所有相关依赖和配置，无需手动添加多个依赖库和配置文件

什么是跨域请求

跨域请求问题是指在 Web 应用中，当一个网页试图从不同的源（域名、协议或端口）请求资源时，浏览器会出于安全原因限制这些请求。这种机制被称为同源策略（Same-Origin Policy），它是浏览器的安全特性，用于防止恶意网站获取用户数据

  1. 使用 @CrossOrigin 注解，在控制器方法或类上添加 @CrossOrigin 注解，以允许特定的跨域请求。这种方法适合需要灵活配置跨域的场景，可以针对不同的请求源进行控制
  2. 可以在 Spring Boot 的配置类中全局配置 跨域资源共享(CORS)，这样应用中的所有控制器都能使用相同的跨域策略。通过实现 WebMvcConfigurer 接口，并重写 addCorsMappings 方法来解决跨域问题。这种方法适合于应用中需要统一管理跨域请求的场景。

Spring Boot 中，拦截器通常通过实现 HandlerInterceptor 接口，并重写其中的方法来实现自定义的拦截逻辑。。

为了使拦截器生效，需要在配置类中通过实现 WebMvcConfigurer 接口，重写 addInterceptors 方法来注册拦截器，添加拦截配置。

对 Spring Boot 事件机制的了解

Spring Boot 的事件机制通过发布订阅模式，主要应用于应用程序中各个组件之间进行消息传递和解耦，通过事件发布和监听机制，实现了不同组件之间的松耦合

事件机制的主要组成部分

  1. 自定义一个事件类继承 ApplicationEvent
  2. 事件发布者是发布事件的组件。可以通过 ApplicationEventPublisher 接口来发布事件
  3. 事件监听器是处理特定事件的组件。可以通过 @EventListener 注解或实现 ApplicationListener 接口来定义监听器。

Spring Boot 支持同步和异步事件传播。通过在事件监听器方法上添加 @Async 注解，可以实现异步处理，提升性能。

  • 在启动类上添加@EnableAsync 注解来启用异步处理
  • @Async 注解标记希望异步执行的方法要注意异步方法是公共的且不能在同一个类中调用

异步方法出现异常 可以在内部处理 try catch捕获，如果你希望在调用者处检查异步方法的结果和异常，可以让异步方法返回 Future<T> 或 CompletableFuture<T>。这样，你可以在调用处使用 get() 方法来获取结果或捕获异常。

#{} 和 ${} 的区别是什么

  • #{}：SQL 参数占位符，MyBatis 会将 #{} 中的内容转换为 SQL 的 ? 占位符，然后在执行 SQL 前使用 JDBC的PreparedStatement 按顺序给 sql 的? 号占位符设置参数值 ，MyBatis 会自动处理传入参数的数据类型转换，并且这种方式可以防止 SQL 注入。
  • ${}是 Properties 文件中的变量占位符，通常用于动态 SQL 生成的场景，在 SQL 中，它会直接将占位符替换为传入的文本内容，但是这种替换没有类型安全，MyBatis 不会对插入的内容进行预处理。

MyBatis 是如何进行分页的？分页插件的原理是什么

  • MyBatis 使用 RowBounds 对象进行逻辑分页，但这种方式会查询所有数据，再截取所需的数据，所以不适合大数据量的场景：
  • 在 SQL 中直接编写数据库的分页语法（如 LIMIT 和 OFFSET）来实现分页
  • 使用PageHelper 插件来完成物理分页。PageHelper 可以自动处理分页参数并生成分页 SQL。
  • 分页插件的基本原理是使用 MyBatis 提供的插件接口，实现自定义插件，在插件的拦截方法内拦截待执行的 sql，然后重写 sql，根据 dialect 方言，添加对应的物理分页语句和物理分页参数。

简述 MyBatis 的插件运行原理，以及如何编写一个插件

MyBatis 使用 JDK 的动态代理，为需要拦截的接口生成代理对象来实现接口方法拦截功能，MyBatis 仅可以编写针对 ParameterHandler、 ResultSetHandler、 StatementHandler、 Executor 这 4 种接口的插件，每当执行这 4 种接口对象的方法时，就会进入拦截方法，具体就是 InvocationHandler 的 invoke() 方法，也可以通过 @Intercepts 和 @Signature 注解来指定要拦截的接口和方法

如何编写插件：

创建一个插件类，实现 MyBatis 的 Interceptor 接口，并重写 intercept() 方法使用 @Intercepts 和 @Signature 注解来指定要拦截的接口和方法。在 MyBatis 的配置文件（如 mybatis-config.xml）或 Spring Boot 的配置类中注册插件。

MyBatis 动态 sql 是做什么的？都有哪些动态 sql？能简述一下动态 sql 的执行原理不？

MyBatis 动态 sql 可以让我们在 xml 映射文件内，以标签的形式编写动态 sql，完成逻辑判断和动态拼接 sql 的功能

MyBatis 在启动时解析 XML 配置文件，将 SQL 模板和动态 SQL 标签转换为一个内部的节点树结构。每个动态标签都对应一个节点，MyBatis 使用 OGNL表达式，从传入的 SQL 参数对象中动态获取属性的值，用于判断条件是否满足 ，当条件为真时，MyBatis 会将对应的 SQL 片段加入最终的 SQL 语句中。MyBatis 将生成 的 SQL 语句与参数绑定后传递给数据库执行，完成查询或更新操作。

MyBatis 能执行一对一、一对多的关联查询吗？都有哪些实现方式，以及它们之间的区别

MyBatis 支持一对一、一对多、多对一以及多对多的关联查询。MyBatis 使用 <association> 和 <collection> 标签来区分不同的关联关系，一对一和多对一：使用 <association> 标签映射单个关联对象。一对多和多对多：使用 <collection> 标签映射集合类型的关联对象。

关联对象查询有两种实现方式：

  1. 多次 SQL 查询：即延迟加载，首先加载主对象，随后根据主对象的属性再分别查询其关联对象。这种方式适用于需要懒加载的场景。
  2. 嵌套查询：通过一次 SQL 查询使用 JOIN 将主对象和关联对象的数据一起查询出来。适用于一次性获取所有关联数据的场景。

join 查询出来 100 条记录，如何确定主对象是 5 个，而不是 100 个？

MyBatis 的去重机制通过 <resultMap> 中的 <id> 标签来实现，MyBatis 会根据 <id> 标签指定的列值判断和合并重复的主对象实例，将关联对象加入到主对象的集合中。

MyBatis延迟加载的实现原理是什么？

在 MyBatis 中，可以通过配置 lazyLoadingEnabled=true 来启用延迟加载机制。MyBatis 使用 CGLIB 或 JDK 动态代理 创建关联对象的代理对象，当调用关联属性的方法时就会进入代理的拦截器逻辑。

例如，当执行 a.getB().getName() 时，拦截器会检查 a.getB() 是否已加载。如果 a.getB() 为 null，则拦截器会执行事先保存的 SQL 查询来获取关联对象 B，然后调用 a.setB(b) 将查询结果赋值给 a 的 b 属性，最后完成 a.getB().getName() 的调用。这就是 MyBatis 延迟加载的基本原理。

MyBatis 的 xml 映射文件中，不同的 xml 映射文件，id 是否可以重复？

不同的 xml 映射文件，如果配置了 namespace，那么 id 可以重复；如果没有配置 namespace，那么 id 不能重复，原因就是 namespace+id 是作为 Map<String, MappedStatement> 的 key 使用的，如果没有 namespace，就剩下 id，那么，id 重复会导致数据互相覆盖。

MyBatis 中如何执行批处理

批处理允许在一个数据库连接上累积多条 SQL 操作，减少数据库交互次数

通过 SqlSession 提供的 ExecutorType.BATCH 模式来执行批处理。

MyBatis 都有哪些 Executor 执行器？它们之间的区别是什么

MyBatis 有三种基本的 Executor 执行器：

  • SimpleExecutor： 每执行一次 update 或 select，就开启一个 Statement 对象，用完立刻关闭 Statement 对象。
  • ReuseExecutor： 执行 update 或 select，以 sql 作为 key 查找 Statement 对象，存在就使用，不存在就创建，用完后，不关闭 Statement 对象，而是放置于 Map<String, Statement>内，供下一次使用。简言之，就是重复使用 Statement 对象。
  • **BatchExecutor**： 是 MyBatis 用于批处理的执行器。调用 update 执行 SQL 操作时，BatchExecutor 会将每个 SQL 通过 addBatch() 添加到批处理队列中，而不会立即执行，这些 SQL 操作会被缓存在不同的 Statement 对象中——每个不同的 SQL 操作或表对应一个独立的 Statement。BatchExecutor 会缓存这些 Statement 对象，以便在执行批处理时可以一次性地执行它们的批量操作。BatchExecutor在 flushStatements() 或 commit() 调用时将所有 SQL 一次性发送到数据库执行。

MyBatis 中如何指定使用哪一种 Executor 执行器？

  • 在MyBatis全局配置文件中，通过 <settings> 标签的 defaultExecutorType 属性来指定 Executor 的类型

  • 使用 SqlSessionFactory 来动态指定 Executor 类型

MyBatis 映射文件中，如果 A 标签通过 include 引用了 B 标签的内容，请问，B 标签能否定义在 A 标签的后面，还是说必须定义在 A 标签的前面？

虽然 MyBatis 解析 xml 映射文件是按照顺序解析的，但是，被引用的 B 标签依然可以定义在任何地方，MyBatis 都可以正确识别。原理是，MyBatis 解析 A 标签，发现 A 标签引用了 B 标签，但是 B 标签尚未解析到，，此时，MyBatis 会将 A 标签标记为未解析状态，然后继续解析剩下的标签，待所有标签解析完毕，MyBatis 会重新解析那些被标记为未解析的标签，此时再解析 A 标签时，B 标签已经存在，A 标签也就可以正常解析完成了。

为什么说 MyBatis 是半自动 ORM 映射工具？它与全自动的区别在哪里？

而 MyBatis 在查询关联对象或关联集合对象时，需要手动编写 sql 来完成，所以，称之为半自动 ORM 映射工具，Hibernate 属于全自动 ORM 映射工具，使用 Hibernate 查询关联对象或者关联集合对象时，可以根据对象关系模型直接获取，所以它是全自动的。

什么是SpringBoot的自动装配

SpringBoot 定义了一套接口规范，这套规范规定：SpringBoot 在启动时会扫描外部引用 jar 包中的META-INF/spring.factories文件，将文件中配置的类型信息加载到 Spring 容器，并执行类中定义的各种操作。如果我们需要引入第三方依赖，只需引入Starter依赖 ，通过少量注解和一些简单的配置就能使用第三方组件提供的功能了

SpringBoot自动装配的原理

Spring Boot 的自动装配是通过 @EnableAutoConfiguration 注解启动的，它利用 @Import 引入 AutoConfigurationImportSelector，该类最终调用 SpringFactoriesLoader.loadSpringFactories 方法，从 META-INF/spring.factories 文件中读取要加载的自动配置类。这些配置类会被加载到 Spring 容器中，供后续的条件筛选使用。接下来，通过 @ConditionalOnXXX 注解判断是否应该创建或注入特定的 Bean。然后Spring 会筛选出自动配置类中符合条件的 Bean 定义，并在需要时实例化并注入到 Spring 容器中，实现按需装配，避免不必要的加载。

Spring的事务在什么时候会失效

在方法上定义了错误的访问权限，就会导致事务失效, 因为spring 要求被代理方法必须是public的

方法用 final或 static 修饰，无法通过动态代理，变成事务方法，这样也会导致事务失效。

在某个 Service 类的某个方法中，调用另外一个事务方法。

一个类没有交给 spring 管理，方法也不会生成事务。

在多线程中用spring事务，可能会导致两个方法不在同一个线程中，获取到的数据库连接不一样，形成了两个不同的事务。

Mybatis的一级缓存和二级缓存

一级缓冲：一级缓存是SqlSession级别的缓存，作用范围在同一个SqlSession中。当我们在相同的SqlSession中，使用相同的参数和SQL语句查询时，MyBatis会优先从缓存中取数据，而不再发送SQL到数据库。一级缓存默认开启，在执行增删改、手动清空、或SqlSession关闭后，一级缓存会失效。

二级缓存：二级缓存存储的是整个 SqlSessionFactory 范围内的查询结果。在同一个 SqlSessionFactory 下创建的SqlSession之间的数据可以共享。二级缓存默认关闭，需要通过在全局配置中启用<setting name="cacheEnabled" value="true"/>或在Mapper文件中使用<cache />标签启用。如果同一Mapper中执行了增删改操作，二级缓存也会自动清空，以确保数据一致性。

一个SqlSession 它代表了与数据库的一次会话，用于管理 SQL 的执行。

mybatis的运行原理

  • MyBatis 首先会加载全局配置文件和 Mapper 文件，解析并加载数据库配置信息、环境信息、映射关系等，然后MyBatis会根据配置创建一个SqlSessionFactory对象 然后通过SqlSessionFactory.openSession()创建SqlSession对象，有了SqlSession对象，我们可以执行Mapper方法或直接执行SQL语句。如果在 Mapper 的配置文件 中配置了动态 SQL，MyBatis首先解析动态SQL，生成最终的SQL语句，并且MyBatis 会通过ParameterHandler绑定参数。然后通过MyBatis的执行器 查询缓存并执行SQL，在SQL执行完成并获取到数据库结果集后，MyBatis会通过ResultSetHandler将结果集映射为相应的实体对象。如果使用了事务SqlSession 提供 commit() 和 rollback() 方法来提交或回滚事务，在使用完 SqlSession 后，调用 close() 方法关闭 SqlSession ，释放资源。

sql 语句where和having的区别

**having vs where**：

  • where：过滤指定的行，不能在where字句中使用聚合函数（分组函数）where 在group by 前。
  • having：过滤已经分组后的结果，一般都是和 group by 连用，不能单独使用。having 在 group by 之后。
  • 因为WHERE 是基于每一行的条件来筛选数据的它的作用范围仅限于每个单独的行。聚合函数是对多行数据进行汇总计算，计算出的是整租数据而不是单独的行

ON和WHERE 的区别

连接表时，SQL 会根据连接条件生成一张新的临时表。ON 就是连接条件，它决定临时表的生成。

WHERE 是在临时表生成以后，再对临时表中的数据进行过滤，生成最终的结果集

连接类型 说明
INNER JOIN 内连接 （默认连接方式）只有当两个表都存在满足条件的记录时才会返回行。
LEFT JOIN / LEFT OUTER JOIN 左(外)连接 返回左表中的所有行，即使右表中没有满足条件的行也是如此。
RIGHT JOIN / RIGHT OUTER JOIN 右(外)连接 返回右表中的所有行，即使左表中没有满足条件的行也是如此。
FULL JOIN / FULL OUTER JOIN 全(外)连接 只要其中有一个表存在满足条件的记录，就返回行。
SELF JOIN 将一个表连接到自身，就像该表是两个表一样。为了区分两个表，在 SQL 语句中需要至少重命名一个表。
CROSS JOIN 交叉连接，从两个或者多个连接表中返回记录集的笛卡尔积

DDD 是一种软件设计方法， 他的很多规范约定，都是为了提高工程交付质量。它所有的手段，都是希望以一个功能逻辑的实现为聚合，将功能所需的对象、接口、逻辑，按照领域划分到自己的领域内。

就像在这个项目中，抽奖中的策略，就是一个独立的领域模型。在这个领域中需要提供策略的装载、随机数算法计算、抽奖模板调用功能，这样一个领域就像划分好的一个独立个体，它拥有属于它的对象信息，当需要使用数据库资源、缓存资源，以及外部接口资源的时候，都通过依赖倒置进行调用。这个领域不做其他模块的引入只负责业务功能实现，所需的所有数据，则有外部接口通过依赖倒置提供。

1、上层模块不应该依赖底层模块，它们都应该依赖于抽象。
2、抽象不应该依赖于细节，细节应该依赖于抽象。

你的抽奖流程中，哪些被定义为值对象，哪些被定义为实体对象

在 DDD 的规范定义中，值对象通常用于描述对象属性的值，不具备唯一ID，不影响数据变化。如；数据库中字段的枚举值、业务流程中属性对象。如抽奖流程中 规则树值对象。

实体对象，则具备唯一ID，会影响到写库动作，抽奖发起实体、奖品信息实体对象

DDD 的分层结构，是以 domain 领域实现为核心，一个 domain 领域下所需的外部服务，都由领域层定义接口，让基础层做具体实现。而数据库持久化操作，定义的 PO 对象，就被这样的方式被限定在基础层了，外部是没法引入使用的，防止了数据库持久化对象进入业务中。

把抽奖划分为抽奖前、中、后，三个动作。请具体结合场景讲解下，为什么这样设计

是什么场景下使用了责任链模式，什么场景使用组合模式，为什么？

模板模式定义了一套标准的抽奖流程 比如进行参数校验、执行责任链 通过规则树进行一个抽奖最终返回抽奖结果，这样的话整个抽奖流程就会很清晰，方便后续的功能迭代，

在设计完抽奖前、中、后，松耦合的结构模型后，对于抽奖前要执行哪种抽奖，但单向选择问题。所以这里使用了责任链模式，进行节点流程判断， 他在执行的时候就会判断是否需要黑名单过滤，没有就走下一个，继续判断你一共消耗了多少积

，如果积分值消耗达到了他的标准就会走权重范围抽奖的一个处理吗，在权重范围抽奖中定义了一些必中的奖品，在对应的库表里有个权重字段，如果前两个都不符合。就有个兜底策略，直接普通抽奖 所以使用责任链更为合适。

之后是进入抽奖的中和后，这两部的流程是相对复杂的，需要判断用户抽奖了几次，对于不同的抽奖会限定是否能获得某个奖品，同时还有库存的扣减，如果库存不足或者不满足n次抽奖得到某个奖品，则会进行兜底。那么这就是一个树规则的交叉流程，所以会使用了组合模式构建一颗规则树，并通过数据库表的动态配置决定在抽奖前完成后，后续的流程要如何进行

抽奖也是一种瞬时峰值很高的业务场景，那么对于抽中奖品后的库存扣减是怎么做的？

关于库存的扣减，是一个非常重要的流程。尤其是这种单独资源竞争的场景，如果设计的不好，很容易把服务打挂

所以在这套系统设计中，为了避免库存扣减直接更新库表的行级锁，而导致大量的用户进行等待状态。所以把数据库表的库存同步到 Redis 缓存中，在通过 incr 扣减的方式进行消费，同时保证不超卖，而对每一条产生从 incr 值，与抽奖的策略ID组合一个key，进行 setnx 加锁兜底，来保证不超卖。

那么最终同步库是怎么做的，怎么降低对数据库的压力的？

保持最终一致性的设计在执行完库存的扣减操作后，发送一个扣减到消息队列，之后通过定时任务来消费队列。通过控制执行频率，降低对数据库的压力

18. 抽奖奖品库存如何处理，怎么保证最终一致性？

这里需要3个步骤，首先是每次扣减完库存，都会写入到 Redis 延迟队列 / MQ 延迟消息，缓慢更新数据库库存。之后是 Redis 内的预热库存消耗完毕后，发送最终 MQ 消息，更新数据库的剩余库存为 0，最终活动结束后，还有任务补偿，扫描抽奖所产生的的参与记录单，更新最终的库存消耗。

. 生产者可能多次发送同一个MQ，怎么保证奖品不会超发？

MQ 的消息是必须含带具有唯一标识的业务ID的。消费者，通过唯一ID业务，更新或者写库的时候可以保证幂等性。如果消息被重复消费，数据库也会拒绝重复的写入操作。这样也就不会产生超发的可能。

在活动开始前会从数据库中获取到N个奖品的抽奖概率，将概率转换为对应的整数数量，写入到缓存中。那么在抽奖的时候就按照整数数量生成随机数来抽奖。这样用空间换时间的效率是非常高的。在项目中使用rabbitmq 消费者在拿到消息的同时 系统宕机了，怎么办

在项目中使用rabbitmq 消费者在拿到消息的同时 系统宕机了，怎么办

消息确认机制：RabbitMQ 提供了消费者确认机制（Acknowledgement）。消费者在成功处理完消息后发送确认，RabbitMQ 才会将消息标记为已处理并从队列中删除。如果消费者还没发送确认就宕机，消息会被重新投入队列，由其他消费者或恢复后的消费者重新消费。这种机制确保了消息不会丢失。

将消息持久化：确保队列和消息都设置为持久化（durable 和 persistent），这样即使 RabbitMQ 或系统本身崩溃，未处理的消息也会保留在队列中，不会丢失。

方法中传入 Channel 和 deliveryTag 参数

  • 通过注解 @Header(AmqpHeaders.DELIVERY_TAG) 可以将 deliveryTag 注入方法中
  • Channel 是 RabbitMQ 客户端和 RabbitMQ 服务器之间的一个通信通道，代表一个会话。所有的消息发送和接收操作都是通过 Channel 完成的
  • deliveryTag RabbitMQ 在消息传递过程中自动生成并维护的一个唯一标识，用来标记每条消息在消费者端的唯一位置。以便在确认或拒绝时引用该消息。

为什么自研路由组件

如果面试问：“为什么要自研，市面不是有吗，怎么回答？” 可以从以下3个点解答；

  1. 维护性；市面的路由组件比如 shardingsphere 但过于庞大，还需要随着版本做一些升级。而我们需要更少的维护成本。
  2. 扩展性；结合自身的业务需求，我们的路由组件可以分库分表、自定义路由协议，扫描指定库表数据等各类方式。研发扩展性好，简单易用。
  3. 安全性；自研的组件更好的控制了安全问题，不会因为一些额外引入的jar包，造成安全风险。

当然，我们的组件主要是为了更好的适应目前系统的诉求，所以使用自研的方式处理。就像shardingsphere 的市场占有率也不是 100% 那么肯定还有很多公司在自研，甚至各个大厂也都自研一整套分布式服务，来让自己的系统更稳定的运行。分库分表基本是单表200万，才分。那么面试怎么说；

  2. 我们的做法是，因为有成熟方案，所以前期就分库分表了。但，为了解释服务器空间。所以把分库分表的库，用服务器虚拟出来机器安装。这样即不过多的占用服务器资源，也方便后续数据量真的上来了，好拆分。
